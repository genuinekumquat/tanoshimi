===============================================================
결정 1. 차단 시 팔로우 관계 자동 해제
===============================================================
A가 B를 차단하면, follows 테이블에 있는 A↔B 간 팔로우 관계(양방향 전부)를
차단 처리와 동시에 삭제한다.

적용 위치: BlockService.block() 내부에서 FollowService의 언팔로우 로직을
호출하여 follower_id/followee_id 조합 양쪽을 모두 정리한다.


===============================================================
결정 2. 차단 여부 확인 방식 — 컬럼 플래그가 아닌 조회 시점 JOIN
===============================================================
논의된 두 가지 방식:

  옵션 A. 컬럼 플래그
    chat_rooms(또는 chat_room_members)에 is_blocked 같은 컬럼을 두고,
    차단이 발생하는 시점에 미리 값을 써둔다.
    - 장점: 조회가 단순하고 빠르다 (컬럼 하나만 확인).
    - 단점: 상태가 user_blocks와 chat_rooms 두 군데에 중복 저장된다.
      차단 해제 시 두 곳을 모두 갱신해야 하며, 한쪽만 갱신하면
      데이터 불일치가 발생할 수 있다.

  옵션 B. 조회 시점 JOIN (채택)
    별도 상태를 저장하지 않고, 메시지 전송/게시글 조회/파티 신청 등
    행위가 발생하는 시점마다 user_blocks 를 조회해서 판단한다.
      EXISTS (
        SELECT 1 FROM user_blocks
        WHERE (blocker_id = :a AND blocked_id = :b)
           OR (blocker_id = :b AND blocked_id = :a)
      )
    - 장점: 상태를 user_blocks 한 곳에서만 관리하므로 불일치가 생기지 않는다.
      차단 해제 시 별도 후처리 없이 즉시 정상 동작으로 복귀한다.
    - 단점: 조회가 한 번 더 붙지만, blocker_id/blocked_id 인덱스로
      비용은 무시할 수준이다.

채택 이유:
  1. dm(1:1) 채팅방은 두 멤버 사이의 차단 여부를 그때그때 확인하는 편이
     구조적으로 자연스럽다.
  2. party(그룹) 채팅방은 여러 멤버가 함께 있으므로, 방 전체에
     "차단됨" 플래그를 다는 방식 자체가 의미상 맞지 않는다.
     A가 B를 차단해도 나머지 멤버와는 정상적으로 대화가 이어져야 하므로,
     결국 메시지/멤버 단위로 조회 시점에 걸러내는 방식이 필요하다.
  3. 상태를 한 곳(user_blocks)에서만 관리하게 되어 동기화 버그 여지가 줄어든다.

결론: chat_rooms 등에 별도 플래그 컬럼을 추가하지 않고,
      user_blocks 테이블에 대한 조회(JOIN/EXISTS)로 차단 여부를 판단한다.


===============================================================
적용 범위 (참고 — TNSM-96 원 스펙)
===============================================================
- 채팅: 차단된 상대와 메시지 송수신 불가
- 게시판/댓글: 서로의 게시글·댓글이 목록/상세에서 숨김
- 파티 매칭: 서로의 파티에 신청 불가 (이미 참여 중인 파티는 그대로 유지)
- UI: 프로필/채팅방에 [차단하기]/[차단해제] 버튼
