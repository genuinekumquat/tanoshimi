[해결됨 — 2026-09-22] 알려진 이슈 — 계획표·웹소켓 파티 멤버십 검증 누락 (TNSM-21)
발견일: 2026-09-22
발견 경위: TNSM-21 "역할 간 연동 안정화"(웹소켓 공용 인프라 - 채팅·플래너, 결제-플래너
           연동 점검) 작업 중, 채팅 쪽에는 있는 "URL만 알고 들어온 비파티원 방어선"
           (PartyService.assertMember / ChatService.assertMember)이 계획표 쪽에는
           하나도 없다는 걸 코드 점검 중 발견함.
상태: 해결됨. feature/TNSM-21-role-integration-check 브랜치에 반영, PR 대기 중.

===============================================================
점검 대상 정정 - "결제-플래너 연동"
===============================================================
티켓 설명에 있는 "결제-플래너 연동 점검"은 이제 해당 사항이 없다. 예약(reservations)·
결제 기능은 migration_v21_remove_reservation_payment.sql 로 이미 삭제됐고,
TripPlannerService/TripPlannerLockService 어디에도 reservation/payment 참조가
남아있지 않다(grep 확인). 계획표는 파티(PartyEntity) 하나에만 연결된다.

===============================================================
증상
===============================================================
로그인만 되어 있으면(파티원이 아니어도) URL의 scheduleId 숫자만 바꿔 넣는 것만으로:
  - 다른 파티의 계획표를 조회(GET /planner/{scheduleId}, .../report, .../route-map)
  - 계획표 항목·저장 스냅샷 목록 조회(GET .../items, .../snapshots)
  - AI 리포트/추천/검증 실행(GET .../report, .../recommend, POST .../ai-validate)
    - 남의 AI 크레딧을 소모시키고 여행 내용을 외부 AI(Gemini)에 흘려보낼 수 있었다.
  - 수동/자동 저장 스냅샷 강제 생성(POST .../save)
  - 계획표 최종 제출/확정(POST .../submit) - @AuthenticationPrincipal 조차 없었음.
까지 전부 가능했다. 편집(항목 추가/이동/삭제)은 편집권(lock) 보유자만 가능해서
직접적인 변조는 막혀 있었지만, 그 편집권을 넘기는 grantLock API 자체가
targetUserId 가 실제 파티원인지 확인하지 않아 파티장이 클라이언트를 조작하면
파티 밖 유저에게 편집권을 넘기는 것도 가능한 상태였다.

웹소켓 쪽은 더 넓게 새고 있었다: WebSocketConfig 의 enableSimpleBroker("/topic")는
로그인만 하면 어떤 destination이든 구독을 막지 않는다. 발행(SEND)은
ChatWebSocketController가 ChatService.assertMember로 막혀 있었지만, 구독(SUBSCRIBE)
자체는 무방비라 /topic/chat/{roomId}, /topic/planner/{scheduleId} 를 직접 구독하면
소속되지 않은 채팅방 대화나 다른 파티의 계획표 변경을 실시간으로 엿볼 수 있었다.

===============================================================
원인
===============================================================
PartyRoomController(파티 전용 화면)는 "party_members 존재 여부로 실제 멤버십을
한 번 더 확인한다(URL 을 안다고 아무나 들어올 수 없게 하는 최종 방어선)"는 원칙을
PartyService.assertMember 로 지키고 있는데, 계획표는 그 파티 화면에서 링크로만
들어가고 실제로는 독립된 /planner/{scheduleId}, /api/planner/{scheduleId}/** 경로라
같은 원칙이 적용되지 않았다. 편집 mutation 들은 우연히 lock 보유 여부로 방어됐지만,
읽기 전용 엔드포인트와 grantLock 의 대상 검증은 애초에 그 방어선을 상속받지 못했다.

웹소켓도 같은 이유 - SEND 는 컨트롤러(ChatWebSocketController)를 거치니 방어선이
붙었지만, SUBSCRIBE 는 브로커가 직접 처리해서 별도로 인터셉터를 달지 않는 한
아무 서비스 코드도 거치지 않는다.

===============================================================
해결
===============================================================
1. PlannerController 에 requireMember(schedule, principal) 헬퍼를 추가하고, scheduleId를
   받는 모든 엔드포인트(뷰 planner/report/route-map, items/snapshots 조회, addItem/save/
   submit, recommend/ai-validate)에 적용 - PartyRoomController와 같은
   PartyService.assertMember 를 재사용한다.
2. TripPlannerLockService.grantLock 이 targetUserId 를 partyMemberRepository로
   검증하도록 수정 - 파티원이 아니면 NOT_PARTY_MEMBER.
3. WebSocketSubscriptionInterceptor(신규, websocket 패키지)를 인바운드 채널에 등록해
   SUBSCRIBE 시점에 /topic/chat/{roomId}, /topic/planner/{scheduleId} 를
   ChatService.assertMember / PartyService.assertMember 로 검증.

수정 범위 밖(의도적으로 그대로 둠): grantLock/revokeLock/rollback 은 원래부터
assertPartyOwner로 보호되어 있어 손대지 않았고, resize/remove/optimize-route/
updateDurationDays 는 편집권(lock) 검사로 이미 충분히 보호된다.
